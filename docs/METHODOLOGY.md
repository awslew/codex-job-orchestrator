# 方法论：三层任务链的多 Agent 协作纪律

> 本文解释一套"领导 / 员工"三段式任务链**为什么这样设计**，而不是复述规则原文。
> 规则模板见 [../templates/AGENTS.strict-delegation.md](../templates/AGENTS.strict-delegation.md)；
> "默认自己干、按需委派"那种形态的差别只在默认值，见 §8。

---

## 1. 这套东西要解决什么问题

把编码 Agent 用久了，会同时撞上四个约束：

1. **上下文是稀缺资源，而且会自我污染。** 读一个大 diff、翻一遍构建日志，就把几万 token
   永久钉在会话前缀里；后续每一轮都要带着它们重发。上下文越满，判断越钝，成本越高。
2. **一个好模型和一堆够用的模型，单位成本差一个量级。** 但"够用"的模型做实现、跑测试、
   翻文件是称职的——把高档模型用在读 diff 上是纯浪费。
3. **并行不是免费的，它的瓶颈不在机器而在人（或领导的注意力）。** N 个任务同时回来，
   验收深度就除以 N。
4. **长任务一旦被打断，从头重做的代价极高。** 需要"续做"语义（保留现场）而不只是"重跑"。

三层任务链是对这四条约束的一组对策：**把执行沉到廉价层，把判断留在贵层，用缓存和
续做控制重发成本，用派单纪律控制并行收益的真实上限。** 它本质上是"把上下文管理问题
转成组织设计问题"。

需要说清的是：这套纪律**不是**"多开几个 agent 就更快"的通用建议，它是一套**有明确成本
结构前提**的工程取舍。前提不成立时，它的开销会大于收益（见 §9）。

## 2. 三层职责划分

```
Tier 1  领导（主会话，你的主模型）
        方案、架构、trade-off、优先级、验收标准、拍板
Tier 2  员工（按任务路由，同一波同 backend）
        claude   : Claude Code CLI          —— 通用实现/修复/测试，支持续做与实时窗口
        luna     : Codex 原生 collaboration —— 复杂推理、跨文件高质量、原生工具能力
        harness  : deepseek-harness         —— 走指定供应商链路，缓存占优、不支持续做
```

三层的分工**不是按"难度"分，而是按产出物的类型分**。这是整份方法论里最容易被误解的一点：

| 产出物类型 | 归谁 | 理由 |
|---|---|---|
| 方案、架构、trade-off、优先级、验收标准 | 领导 | 这些是"判断"，判断一旦外包，领导就只剩转述功能 |
| 实现、修复、测试执行 | 员工 | 可验证、有客观判据、失败可窄修复 |
| 现状取证、审计（事实表 + 硬约束 + 未知项） | 员工 | 事实采集是带宽活，不是判断活 |
| 把**已定**方案落成代码/文档 | 员工 | 方案已定，执行无自由度 |

### 2.1 为什么领导不该亲自实现

三条理由，按重要性排序：

1. **上下文是领导的判断力来源。** 领导亲自读完整 diff，得到的事实并不会让它拍板更准——
   员工给的"事实表 + 验收逐项"信息量更密，体积小两三个数量级。领导亲自读文件的真实后果
   是：占用掉后面几次决策的注意力预算。
2. **成本结构不划算。** 主模型通常是最贵的一档；把它当实现器用，等于用最贵的 token 干
   最可替代的活。
3. **角色混同会破坏验收。** 自己写的代码自己验收，等于没有独立验收环节。让员工实现、
   领导验收，天然形成一道检查。

但这里有个**关键例外，而且它是整份规则的高潮**：

> **动脑本身不能外包。** 员工可以列"选项 + 利弊对照"，但结论、建议、方案成文必须领导亲写。
> 员工回传里的"建议采用 X / 推荐方案"一律视为**无效输入**。

理由不是"员工能力不行"，而是：**员工看不到完整的决策上下文**（用户偏好、历史包袱、
未说明的约束、成本预算）。它给出的"建议"是在信息不足的前提下做的局部最优解，看起来
很合理，但领导一旦直接转述，就把一个**信息缺失的判断**伪装成了**领导的决定**。
一旦这种转述成为习惯，领导层就退化成"转发器"——而转发器是个可以被删掉的组件。

这就是"防领导变中转"的判据：**用产出物类型判断该谁做，而不是用任务难度判断。**

### 2.2 派单前自检

一个可执行的检验：**删掉所有调度器样板文字，如果 prompt 里只剩一个开放式问题**
（"请设计…""请给方案…""如何优化…"），**这次派单就越界了**——因为你在把"想清楚"这件事
派出去。合法的派单，prompt 里必须已经有：已定方向、约束、或者候选选项。

### 2.3 员工的统一回执契约

三类员工回传的格式必须一致、且**故意窄**：

```
status │ backend/agent type │ 变更文件或取证位置 │ 验收逐项 │ 自测结果 │ 剩余风险/未知项
```

**禁止**：完整 diff、完整日志、长篇思考。这不是洁癖——回执是唯一会进入领导上下文的东西，
它的体积直接决定领导能同时处理几个任务。**回执宽度 = 领导带宽的输入参数。**

## 3. 路由决策：按 backend，不按模型名

### 3.1 为什么是 backend 而不是模型名

这是全套规则里最容易被抄错的一条。直觉上，路由应该问"哪个模型最强"，但实际决定成败的是
**四件跟模型名无关的事**：

1. **能力面不同。** 某个 backend 有原生浏览器/文档/可视化工具，另一个没有；这不是模型
   强弱问题，是"能不能做"问题。
2. **会话语义不同。** 有的 backend 支持真正的 session resume（`--resume` 续前缀），有的
   只支持"新的独立 turn"。**把后者称作"续做"是语义欺骗**，会让领导误以为上下文还在，
   写出依赖已丢失上下文的指令。
3. **可见性不同。** 有的支持实时 live 窗口与 attention 审批事件，有的两者都没有——这直接
   决定领导能不能及时发现"卡住了"。
4. **缓存行为不同（见 §4）。** 缓存命中按 **backend 的系统前缀**分桶。两个 backend 即使
   跑同一个模型，也不能共享缓存前缀。

所以正确的路由单位是 **backend（及其 profile/effort）**，模型名只是该 backend 的一个配置项。

### 3.2 路由决策树

```
用户显式指定了 backend？ ── 是 ─▶ 用它（用户指定最高优先，不再优化）
        │ 否
        ▼
任务是否必须用某 backend 的原生能力（浏览器/文档/可视化）？
        │ 是 ─▶ 用具备该能力的 backend（通常是原生 subagent 侧）
        │ 否
        ▼
是复杂推理 / 跨文件高质量实现 / 该链路边界外的任务？
        │ 是 ─▶ 走"重推理"backend
        │ 否
        ▼
需要同任务续做/修复（resume/reply 语义）？
        │ 是 ─▶ 必须选支持真实 resume 的 backend（不支持的那个只能开新 turn）
        │ 否
        ▼
某 backend 的缓存/成本显著占优，且任务是"一趟干完"型？
        │ 是 ─▶ 用缓存占优的 backend
        │ 否
        ▼
默认：通用实现/修复/成熟工具链 ──▶ 通用实现 backend（成本最低、链路最稳）
```

两条补充纪律：

- **用户显式指定 > 一切自动优化。** 自动路由是默认值，不是特权。
- **"重推理 backend"不是失败兜底。** 它拥有独立的能力面，应该按上面的判据**主动**路由；
  把它当"其它都失败了再试试"的兜底，会让路由退化成随机重试。

## 4. 上下文与缓存经济学

### 4.1 核心事实：每轮都是全量重发

对话式 Agent 的每一轮请求都要把**完整上下文**重新发给模型。计费通常分两档——
**前缀命中**与**未命中**。作者在自己的环境下观测到的量级差异是**约 31 倍**
（命中约 $0.014/M vs 未命中约 $0.44/M；**这是作者环境下的观测值，不同供应商/不同时期
的定价与缓存策略差异很大，不要当普适常数**）。

推论：**"续做"比"重开"便宜得多，而"冷启动"是最贵的操作。**

### 4.2 为什么"同波同 backend"能保热

缓存键作用在**系统前缀**上——即系统指令 + 工具定义 + 固定协议块这些每次请求开头都一样的
部分。同一个 wave 里的多个 job 由同一 backend、同一 profile 启动，它们的系统前缀**逐字节
相同**。于是：

1. 第一个 worker 首次落盘后，前缀进入供应商的公共缓存；
2. 其余 worker 的首次请求在秒级内命中同一前缀，**跳过冷启动**。

这解释了两条看起来反直觉的规则：

- **独立任务要并发齐发，不要"为了看清"改串行。** 第一个 worker 的冷启动成本会被同一 wave
  的其它 worker 摊掉；改成串行反而每颗都是冷启动。
- **wave 之间不要插入孤立单任务。** 它跟任何同波成员都不同前缀，等于自己付一次全量 miss。

反例同样重要：**跨 backend、跨 effort 的 wave 保热失效**——系统前缀不同，缓存分桶不同。
所以纪律是"不同 backend 拆 wave，同一 wave 同 backend"。

### 4.3 批处理窗口内的"三不动"

**升级员工 CLI、中途换模型映射、改全局指令文件**——这三件事里任何一件都会让所有 worker
的系统前缀**齐变**，导致整批一起冷一次（≈ 每个 worker 一次全量 miss）。所以全局变更要安排
在无任务的时候做。这不是"运维建议"，而是缓存键的直接推论。

### 4.4 续做的语义按 backend 分流

| backend 类型 | 续做方式 | 语义 |
|---|---|---|
| 支持真实 resume 的 CLI | 同一 jobId 走 reply（继承 sessionId，`--resume` 续前缀） | 真续做，前缀命中延续 |
| 原生 collaboration subagent | 走该框架的 followup 机制 | 员工侧保留现场与改动 |
| 仅支持独立轮次的 backend | 开新 start（`allowFreshTurn`） | **新的独立 session/turn，不是 resume** |

最后一行值得强调：**没有 resume 语义时不得称"续做"**。称呼错了，领导就会写出"按你上轮
说的继续改"这种指令，而员工那边其实什么都没有——这是最难排查的一类失败。

配套的判断：**长任务拆成 N 个串行 start 是最贵的写法。** 每个 start 都是一次全量 miss。

## 5. 并行派单的三轴判据

### 5.1 为什么"文件集不重叠"不等于独立

这是这套方法论里最贵的一个教训。两个任务改完全不同的文件，看起来天然可并行——但如果
B 的接口命名、错误处理模式、目录约定应当**继承 A 被验收后的做法**，那么并行就是错的：
你会在 A 的验收结论出来之前，让 B 按自己的猜测定型。等 A 被验收（并且改了一点约定），
B 的产出就整份作废。**N 个实现一起作废重来**，比串行慢得多。

所以判据从"有没有产物依赖"升级成**三轴**：

| 轴 | 判据 | 处理 |
|---|---|---|
| **产物依赖** | B 需要 A 的产物/结论才能开工 | 串行：等 A 终态后 start，或走 reply 链 |
| **决策依赖** | B 的实现约定应继承 A 的做法（接口/命名/模式） | 先发 A，B 以 A 的钉子为输入；**或领导先把契约钉死再齐发** |
| **真独立** | 三轴全过 | 齐发：连续 start N 次，拿到 jobId 立即发下一个 |

第二轴的处理给了两条出路，第二条常被忽略却最有效：**如果领导愿意花五分钟把接口契约钉死，
决策依赖就消失了**，任务立刻变成真独立。这是"领导做判断"能直接换来并行度的地方。

### 5.2 齐发前 30 秒自检

拆解完的任务默认进入"齐发候选"，派单前依次过三问：

1. 有**决策耦合**吗？
2. 有**共享派生空间**吗（install/build/lock/测试产物交集）？
3. 我的**验收带宽**够吗？

三问全过才齐发。**自检命中而选择串行/错峰不是失败，是判断。**
（早期版本把"串行循环"写成禁止行为，那是过度矫正，后来被正式废除。）

### 5.3 派生空间隔离：文件集铁律的第二层

源文件集不重叠还不够，还要声明**无 install/build/lockfile 交集**：`node_modules`、`dist`、
构建缓存目录、测试产物、截图目录。两个 worker 同时跑 install 或 build，会在同一批派生文件
上互相踩。git 操作同理——波内单 worker 独占，避开 `.git/index.lock` 争锁。

### 5.4 为什么"验收带宽"是并行的真实上限

这是整套纪律里最诚实的一条：**并行 wave 的收益上限不是 worker 数，而是领导的验收带宽。**

N 个 job 同时终态，意味着每份摘要分到的验收深度是 1/N。"验收只看回传摘要"本身就是一层
打折的兜底（相对于亲眼看代码），在并行时再降到"只扫标题"，验收环节就名义存在、实质失效。
**并行度超过验收带宽之后，多出来的 worker 只在制造"看起来跑得快"的假象。**

实践做法：

- start 端齐发，**反应端逐 job 独立**（先到先收）：成功即验收、腾注意力，失败立即修该 job。
  **绝不等全波 settle 才动手**——等齐只是把空等从 start 端搬到反应端。
- 同刻终态超过可验收数时，**优先验收影响下游的 job**，其余排队。

### 5.5 并发的"定容"而不是"定值"

不要设一个固定的"同时最多 N 个 worker"。容量应由**结构化准入**决定：安全上限、内存预留、
`resourceClass=heavy` 的任务、派生空间冲突、backend profile，共同产生一个 `queueReason`，
超出的排队。共享运行时资源（端口/DB/部署目标）或需 git 独占的操作 → 直接串行。

配额的纪律同样属于这一节：已知配额临近、或最近 wave 出现过供应商限流 → **降容或串行**。
不要把配额耗尽做成"整批一起失败"。

### 5.6 两个容易混淆的并发参数

| 参数 | 管什么 | 范围 |
|---|---|---|
| `internalAgentParallelism` | **单个 worker 内部**拆子 Agent 的并行度 | auto/1-4 |
| `desiredWorkerConcurrency` | **领导层**同时派多个 worker | 1-64（资源准入后取实际值） |

两者**正交**。文件集单写者纪律属于前者（一个任务内部也只有一个文件写者）。默认齐发派单时
用缺省 `auto` 即可，不要为"并行"显式传参。

## 6. 权限与安全边界

### 6.1 三档 profile 的分工

| profile | permission-mode | 用途 |
|---|---|---|
| `auto` | `bypassPermissions` | 实现/修改/测试（默认档）：不逐项审批，**也没有沙箱** |
| `review` | `plan` | 只读取证、审计、风险排查；产出报告时只放行报告文件写入 |
| `normal` | `acceptEdits` | 人工控制 / 故障回退 |

设计要点：

- **`auto` 档的准确语义要说清楚（别高估它）。** worker 以你的用户身份运行、无人值守、不会为任何
  一步停下来问你——"没写进 `allow`"**不等于**被拦，`deny` 才是唯一真正拦住调用的规则类型。而
  `deny` 是**可绕过的字面前缀黑名单**（换个写法、写进脚本、经 `npx` 间接调用都命中不了），
  **不是沙箱**。所以 auto 档适合"你本来就会让它做的事"，不适合"你想让它做不了的事"。
- **`deny` 是地板，不是可覆盖的默认值。** 文件缺失时用完整的内置默认拒绝清单兜底；文件里写了
  `deny` 时，生效的是**内置基线 ∪ 你的规则**——你的规则一律生效，基线里你漏掉的自动补齐。
  **基线只能加、不能减**：写配置的人（你、一份拷来的模板、甚至被注入改写的文件）只能把策略
  **收紧**，无法让产品停止拦截不可逆操作。所以随仓库发的 `templates/worker-whitelist.json` 只是
  **起点而非全部**，比基线窄的部分会被补齐（并留下一条 `worker whitelist incomplete … Nothing is
  broken` 的告知性提示）。`allow` 的语义相反：**授权按你写的原样使用，绝不替你放大**。
- **只读档的产物契约要显式。** review 档 + 研究/分析类任务（带明确的报告路径）是合法组合：
  调度器自动切成"只放行报告文件写入"的派生模式。这样"只读"不必等于"不能留证据"。
  但如果不产出文件，就不要给报告路径——纯摘要回传更干净。
- **不要对只读会话反复重试同一次写入。** 如果员工反复卡在"写报告被拒"的审批点上，
  说明调度器行为异常：**取消后重派**，而不是对它 reply 重试 N 次。

### 6.2 为什么"权限分类器"被拆掉了

早期设计里，每次工具调用前插一个模型分类器决定是否放行。它的实际表现：每次都发起一次额外
模型请求，经共享链路时**持续超时**、阻塞已经批准的操作、并反复消耗额度。结果是安全机制
变成吞吐瓶颈。

后来的取舍是：**auto 档不用模型分类器，改为确定性 deny 清单**——运行时全通过，唯一能拦住调用的
是**每 job 独立注入的 deny 规则**（`git push` 一律人工执行、shutdown/format、系统目录写保护…），
而不是逐项审批。要点有四：

1. **确定性优于概率性。** deny 规则是字符串匹配，不会超时、不会误判、不会消耗额度。
2. **不依赖全局配置。** 权限由调度器**每个 job 独立注入**，这样外部工具重写全局 settings
   也抹不掉它——这是"配置漂移"的一种防御。
3. **不许静默越权。** 只有 `auto` 档需要校验回执里的 permission-mode；如果回执显示没有
   按预期生效，**停止重派、先修配置**。review/normal 档按自身档位规则执行，不加额外约束。
4. **安全敏感的任务不要放在 auto 档**，改用 review 档或人工执行。理由不在"分类器没了"，
   而在**这一档根本没有沙箱**：worker 以你的身份运行，能被拦住的只有 `deny` 命中的那些写法，
   其余一律照做（见 6.1）。

### 6.3 别把限流误报成权限问题

一个具体的错诊模式：任务失败 → 看到"需要审批/失败"字样 → 归因为权限配置。正确的判别是
**看 `failureDetail` 原文与结构化 `substatus`**：

- `substatus=upstream_rate_limited` → 供应商额度触顶：等 reset 或换端点，**重试无意义**；
- `substatus=upstream_unavailable` → 上游 502 风暴：稍后重派即可；
- 真正的审批卡点才叫"需要人工介入"。

**把限流当成审批去 reply，只会白烧额度。**（这条陷阱的通用形态是：失败信息很含糊时，
人会往自己最近改过的地方归因。所以纪律是**看原文**，不是看印象。）

## 7. 常见误用与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 派一个开放式问题（"请设计…"）给员工 | 把"想清楚"外包，员工缺上下文，结论不可采纳 | 先自己定方向/约束/候选，再派执行 |
| 直接把员工的"建议采用 X"转述给用户 | 信息缺失的判断被伪装成领导的决定 | 自己重新推导，或打回重做 |
| 为"看清楚"把独立任务改串行 | 放弃同波前缀保热，每颗都冷启动 | 独立任务齐发，靠回执与窗口看进度 |
| 把文件集不重叠当成独立 | 忽略决策依赖 → N 个实现一起作废 | 用三轴判据；或先钉死契约 |
| 长任务拆成 N 个串行 start | 每个 start 都是一次全量 miss | 用续做链（reply / followup） |
| start 齐发后用"等齐"来收 | 把空等从 start 端搬到反应端 | 逐 job 独立 watch，先到先收 |
| 对不支持 resume 的 backend 说"续做" | 语义欺骗 → 领导误以为上下文还在 | 表述为新 session/turn |
| 批处理中途升级 CLI / 换模型映射 / 改全局指令 | 整批前缀齐变 → 全体冷一次 | 全局变更安排到无任务时 |
| 为省事让两个 worker 跑同一目录的 install/build | 派生文件互踩、lock 争锁 | 派生空间不重叠，或提前统一预热 |
| 并发数拉满 | 验收带宽被除以 N，验收名义存在实质失效 | 按准入定容，优先验收影响下游的 job |
| 权限出问题就加分类器/逐项审批 | 每次调用多一次模型请求，成为吞吐瓶颈 | 确定性 deny 白名单 + auto 档全通过 |
| 把失败一律归因为权限 | 限流被当成审批，白烧额度 | 看 `failureDetail` 原文与 `substatus` |

## 8. 与「可选委派」模式的关系

本文描述的"强制委派"是**一种**配置，不是唯一形态。它的规则形态是：

- 全局规则文件里写明"实现一律派活"；
- 领导默认不实现，只在必须用主模型原生能力时才亲自执行；
- 三档 profile、缓存纪律、并行纪律全部生效。

另一套形态是"**默认自己干、按需委派**"：

- 主模型默认完成理解、读取、设计、实现、诊断、测试与验收；
- 只有当**当前任务的用户明确要求**委派时，才调用员工工具；
- 员工工具的存在与安装**不构成授权**。

两者的技术底座相同（同一套 job 模型、profile、缓存与可见性机制），差别只在**默认值**。
值得注意的是：作者本人后来从"强制委派"演进到了"按需委派"作为主线的模式——这不是对前者的
否定，而是因为成本结构与任务分布变了（见 §9）。**把默认值当教义是这套方法论最容易被误用的
地方；它本来就是可配置项。**

## 9. 这套方法论的适用范围与争议

诚实地说：**它不是普适最佳实践。**

### 它的主要代价

1. **交接开销。** 每次派单都要写 bounded task（目标 / 允许修改范围 / 验收标准 / 验证命令 /
   权限边界 / 修复轮次上限）。任务越小，这份固定成本占比越高——小于一定粒度的任务，
   派单本身就比干活贵。
2. **上下文丢失。** 员工的回执是**故意压窄**的。领导看不到实现过程里的细节，某些只有
   "顺着看代码才会发现"的问题，会漏在领导视野之外。
3. **延迟。** 派单 → 启动进程 → 执行 → 等待 → 验收，链路比直接干长。对小改动，
   往返延迟远大于执行时间。
4. **缓存与并行的纪律是一种额外约束。** 不能随时升级 CLI、不能随时换模型映射、
   不能随便混波——这些限制在"一个人一把梭"的模式下不存在。
5. **纪律本身需要执行成本。** 三问自检、三轴判据、回执格式，都要靠人（或领导模型）
   每轮真的去做；不执行的话，它只是文档里的一段漂亮话。

### 它明显划算的场景

- **主模型额度单价远高于 worker**（本方法论的原始前提，也是最强的适用条件）；
- 任务天然可切块，且切块后能通过**钉死契约**变成真独立；
- 工作量大到足以摊平派单的固定开销（长时间实现、批量审计、多文件重构）；
- 有多个异构 backend 提供**不同能力面**（原生工具、续做语义、缓存优势），
  路由本身能换来真实收益。

### 它明显不划算的场景

- 小改动、单点修复、探索性调试——往返延迟与派单开销会吃掉全部收益；
- 强决策耦合、无法预先钉死契约的任务——并行会带来整体返工；
- 上下文连续性至关重要的任务（长链推理、逐步收敛的疑难排查）——每次交接都在丢信息；
- worker 与主模型成本结构接近时——省不下钱，只剩开销。

### 争议点

- **"领导不读代码"是否安全？** 支持者的理由是摘要层的信噪比更高；反对者的理由很硬：
  摘要由被验收方自己写，等于让被考核者自评。缓解手段是把"取证"也当独立任务派出去
  （员工只产事实表，不下结论），以及把 lint/typecheck/test/build 当作**机器的**验收证据——
  但它缓解不了"摘要没提到的问题"。
- **并行度与质量是否真的可以解耦？** §5.4 的结论是悲观的一侧的：并行上限受验收带宽约束。
  这等于承认"加 agent"不会线性加速——在某些任务上，它只是把一个瓶颈换成了另一个。
- **强制委派的纪律成本会不会超过收益？** 取决于任务粒度分布。如果日常任务以一两小时以上的
  实现为主，纪律成本被摊薄；如果以小改动为主，强制委派基本是净损失。

**一句话总结**：这是一套针对"**主模型贵、worker 便宜、任务可切块**"这三个条件同时成立的
成本结构而设计的纪律。条件成立时它能显著省钱并保护上下文；条件不成立时，它就是一层多余的
官僚流程。作者本人后来把默认值改成了"自己干、按需委派"，本模板作为**可选**形态保留——
请按自己的成本结构判断，而不是照搬。
